An orders lakehouse on GCP

Raw orders land in Cloud Storage, sorted by the day they arrived. Each day, Spark reads only that day's files, cleans and dedupes them, and BigQuery rebuilds only the dates that changed. I tested it on about 31 million synthetic orders, with late arrivals, corrections, duplicates and one deliberately broken file, and measured everything.

The lakehouse was the last day of a 14-day series where I moved what I know from the Hadoop stack over to Google Cloud, one topic a day: IAM, BigQuery, Dataproc, Pub/Sub, Dataflow, Terraform and more. All 14 days together cost $0.17 in credits.

fun fact: a managed Airflow (Cloud Composer) would cost ~$300 a month. The orchestrator was the real bill!

Azure Service BusADLS Gen2RedisFunctionsKey Vault

An event-driven order pipeline on Azure

A seven-day plan to learn Azure's data and messaging services properly, with 4 of 7 days done so far. Everything is set up from the command line, and every service signs in with a managed identity, so there are no passwords or keys anywhere in the code.

Orders arrive in Blob Storage, go through Service Bus, and end up as bronze, silver and gold Parquet in a data lake. The consumer is idempotent: 4 deliveries of the same orders produce exactly 3 invoices.

things I learned the hard way

  • An Azure "Owner" can't read what's inside a blob. Managing a resource and reading its data are separate permissions.
  • Turning on blob versioning quietly changes what "delete" means.
  • Azure stopped offering its Cache for Redis halfway through my project, so the Redis part runs in Docker instead.
